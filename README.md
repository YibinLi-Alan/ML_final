# 💳 Credit Card Customer Churn Prediction

An end-to-end machine learning system that predicts credit card customer churn for retail banking. A Random Forest classifier wrapped in a Streamlit web interface and deployed on AWS (S3 + EC2).

Built as a proof-of-concept capstone project — covers the full lifecycle from EDA and model training to cloud deployment and a working user interface.

## 🎯 The Problem

Credit card customer attrition is expensive — acquiring a new customer costs roughly **5×** more than retaining an existing one, and a 5% improvement in retention can lift profit by up to **85%**. Most banks only find out a customer is leaving after the account has already been closed.

This project flags at-risk cardholders **before** they cancel, so a retention analyst can intervene with a phone call, fee waiver, or targeted offer.

**End user:** A bank retention analyst who reviews flagged accounts each morning and decides how to reach out — not an engineer, not a data scientist.

---

## 🏆 Results

Random Forest beat the alternative (a 3-layer MLP) on every metric on the held-out test set:

| Metric | MLP | Random Forest | Δ |
|---|---|---|---|
| Recall *(primary)* | 0.784 | **0.865** | +0.081 |
| Precision | 0.716 | **0.865** | +0.149 |
| F1 Score | 0.748 | **0.865** | +0.117 |
| ROC-AUC | 0.963 | **0.989** | +0.026 |
| Accuracy | 0.923 | **0.961** | +0.038 |

**Recall** is the headline metric here — missing a churner means losing the account forever, while a false alarm just costs an unnecessary phone call. The 8-point Recall improvement translates to catching about 8 more at-risk customers out of every 100 before they close their cards.

## 📊 The Data

**Source:** [BankChurners dataset (Kaggle)](https://www.kaggle.com/datasets/sakshigoyal7/credit-card-customers)

- **10,127** real credit card customers
- **19** usable features after dropping two pre-computed Naive Bayes columns that leaked the target
- **16.1%** churn rate — imbalanced, addressed with **SMOTE on the training set only** (validation and test kept their natural distribution)
- **Split:** 80% train / 15% validation / 5% test (stratified)

**Feature groups:**

| Group | Examples |
|---|---|
| Demographics | Age, gender, dependents, education, marital status, income bracket |
| Account profile | Card category, months on book, products held, months inactive |
| Financial signals | Credit limit, revolving balance, transaction counts and amounts, Q4/Q1 changes, utilization ratio |

The most predictive features turned out to be behavioral: **Total_Trans_Ct**, **Total_Trans_Amt**, **Total_Revolving_Bal**, and **Total_Ct_Chng_Q4_Q1**.

## 🌲 The Model

**Random Forest Classifier**

- 300 trees, default depth, scikit-learn `RandomForestClassifier`
- Trained on SMOTE-balanced features after one-hot encoding and standardization
- Same preprocessing pipeline used at inference time (the `scaler` and `feature_columns` are persisted with the model so production matches training exactly)

### Why Random Forest over a neural network?

1. **Higher Recall on the same problem** — and Recall is what matters here.
2. **Interpretable by design** — feature importances are exposed natively, so an analyst can see *why* a customer was flagged.
3. **Sub-millisecond inference** — scores a single customer in under 1 ms on CPU. No GPU, no PyTorch, no heavy framework.
4. **34 MB total artifact** — the full model plus preprocessing fits in less than 40 MB, making cloud deployment trivial.

The full comparison and modeling work lives in [`memo1.ipynb`](memo1.ipynb).

## 💻 The App

A Streamlit interface designed for a retention analyst, not a developer.

**Three-column input layout:**
- **Demographics** — age, gender, dependents, education, marital status, income
- **Account activity** — card category, months on book, products held, inactivity, contact count
- **Financial signals** — credit limit, balance, transaction amounts and counts, Q4/Q1 deltas, utilization

**Output:**
- A churn probability (e.g. *0.87*)
- A color-coded risk tier — **High** (≥70%), **Medium** (40–70%), **Low** (<40%)
- A plain-English recommendation for next action

The design choice: the most prominent element on the result screen is the recommendation, not the raw probability. The probability is for analysts who want to dig deeper; the recommendation is what they actually act on.

## ☁️ AWS Deployment

A simple, three-service architecture appropriate for a POC:

```
                                ┌─────────────────────────────────────────┐
                                │  AWS Academy · us-east-1                │
                                │                                         │
   Browser                      │   ┌──────────────┐   ┌──────────────┐   │
   (analyst)  ──── HTTP :8501 ──┼─► │  EC2 t3.small│◄──│   S3 Bucket  │   │
                                │   │  Ubuntu 22.04│   │  (3 .pkl     │   │
                                │   │  Streamlit   │   │   artifacts) │   │
                                │   │  tmux daemon │   └──────────────┘   │
                                │   └──────────────┘                      │
                                │           ▲                             │
                                │           │ IAM (LabInstanceProfile)    │
                                │           │ + Security Group (8501,22)  │
                                └─────────────────────────────────────────┘
```

**Services:**
- **S3** — durable storage for model artifacts (`rf_model.pkl`, `scaler.pkl`, `feature_columns.pkl`)
- **EC2 (t3.small)** — runs the Streamlit app, pulls artifacts from S3 on boot via the AWS CLI
- **IAM + Security Group** — `LabInstanceProfile` lets EC2 read S3 without hardcoded keys; Security Group exposes port 8501 publicly and restricts SSH

**Why not SageMaker?** The model was already trained locally — there was no need to send a 34 MB pickle up to a managed training service just to send it back down. EC2 + S3 + Streamlit is the right size for a single-user POC and keeps cost and complexity low.

The Streamlit process runs inside a `tmux` session so the app survives SSH disconnects. Predictions return in under 1 second end-to-end.

## 🔧 Run Locally

```bash
# 1. Clone
git clone <your-repo-url>
cd <your-repo-name>

# 2. Set up a virtual environment
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate

# 3. Install dependencies
pip install streamlit==1.56 scikit-learn==1.7.2 pandas numpy joblib imbalanced-learn matplotlib seaborn

# 4. Open the notebook to train the model and generate the .pkl artifacts
jupyter notebook memo1.ipynb
# Run all cells — it will save rf_model.pkl, scaler.pkl, feature_columns.pkl in the working directory

# 5. Launch the app
streamlit run app.py
# Open http://localhost:8501 in your browser
```

## 📌 Notes & Limitations

- This is a proof-of-concept, not a production system. No authentication, logging, or batch scoring (yet).
- The deployed EC2 endpoint is short-lived — it's running in AWS Academy, which expires lab sessions every 4 hours and reassigns public IPs on restart.
- Retraining is manual. A production version would schedule retraining via Lambda or a cron job to keep up with shifting customer behavior.
